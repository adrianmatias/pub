From Ambiguity to a Trusted AI System

Models are commoditizing and first drafts got cheap. What stays scarce is deciding what «correct» means, picking the lowest rung that holds, proving the boundaries red, and handing over a system a team can operate without its author.

Adrian Matias 25 Nov 2026 ~5 min read public method · zero client material

The short version

Across eleven years of applied ML FACT [6] (scoring, ranking, fraud, financial NLP) and recent enterprise LLM work, systems rarely fail because the model lacked parameters. They fail because nobody fixed the decision cost before modelling, because an LLM was given work a deterministic check should own, because offline and online features drifted apart, or because an impressive demo hid a broken edge case. Every durable deployment follows the same six stages.

Stage 01Start from the decision and its error cost

A request usually arrives as a model wish: «classify these documents», «build an agent to automate bookkeeping», «improve our ranking model». The first hour is spent refusing to talk about models until four facts are written down in plain language:

  • The action taken on the output. Does the system execute autonomously (straight-through processing), draft a suggestion for a domain expert, or abstain and escalate?
  • The cost asymmetry. In high-trust workflows — fraud filtering, financial categorization, enterprise vendor assessment, real-time bidding — a silent wrong automation destroys user trust far faster than a conservative abstention.
  • The decision metric with uncertainty. Aggregate accuracy hides the operating point. A better contract fixes the metric that moves the business — for example, automation coverage at a capped human-correction rate, or expected loss under a posterior spread when rewards are scarce — instead of a point estimate where 7/10 looks identical to 70/100.
  • Quoted requirements, not paraphrases. Ambiguous business rules get quoted verbatim from the domain expert or specification. When engineers or coding agents work from paraphrased summaries, review quietly checks the code against the paraphrase rather than against intent [1].

Stage 02Choose the lowest rung that works

Starting from a favourite model family is backwards. Every subtask in a real workflow belongs on the simplest rung that meets the error budget:

rungwhen it winstypical failure when misused
1 · Deterministic logicKnown invariants, arithmetic, schema validation, exact rules, lookups, reconciliation math.Handing arithmetic or exact accounting checks to an LLM turns a 0-error rule into a probabilistic leak.
2 · Classical MLStructured tabular signals, calibrated probabilities, imbalanced risk/fraud, fast CPU latency, strong baselines.Jumping to neural nets or LLMs before a clean gradient-boosted baseline tells you whether signal even exists.
3 · Deep learning / embeddingsHigh-cardinality entities, transfer learning across cold-start items, semantic retrieval, dense representation.Training bespoke towers without locking feature parity between offline training and online serving.
4 · Generative AI & agentsUnstructured documents, zero/few-label cold start, open-ended synthesis, multi-step tool orchestration.Shipping thin prompt wrappers with untyped output, unmeasured hallucination, and no fallback path.

In practice, the fastest path combines the top and bottom rungs: ship a walking skeleton on day one — data in, decision out, a number a human can inspect — letting an LLM carry rough stages early so real failure modes surface immediately. Then, round by round, distil deterministic steps back into typed code until only irreducible judgement remains generative [2].

Stage 03Model the domain, render the ontology, freeze the boundary

Prompt wording will change every week; models and vendor SDKs will change every quarter. What has to stay rigid is the domain ontology — the named concepts, closed vocabularies, and boundaries between probabilistic generation and business rules.

  • Domain-Driven Design (DDD) as an anti-hallucination device. Eric Evans's ubiquitous language and bounded contexts were written for human teams [7]; with coding agents they become load-bearing. Without explicit domain terms, agents invent competing synonyms across files and drift into loose utility functions patching one another. Matt Pocock has popularized turning this into concrete agent skills — grilling requirements before code (/grill-me) and enforcing a checked glossary and domain model (domain-modeling) so fuzzy terms get caught before an implementation wave multiplies them [8].
  • Clean Architecture and OOP boundaries at machine speed. Robert C. Martin's («Uncle Bob») Dependency Rule — source dependencies point inward toward domain entities and policy, never outward toward frameworks, databases, or LLM providers [9] — turns from craft preference into a survival constraint when agents generate code. Agents pattern-match the repository rather than prose wikis: one leaked SDK or persistence call inside core logic gets copied across every new module. In ini, a concept is a named class owning its data and rules, a component is a package, and an AST gate (shape) caps free functions per module (PILE ≤ 6) while confining CLI/run wiring to the outer shell [2].
  • AST-rendered ontology, never hand-drawn maps. Architecture diagrams maintained by hand silently rot across refactors. Rendering the project ontology directly from Python's AST (python -m ci domain --write) turns the component graph, entity inventory, and acyclic import edges into a mechanical check: if code drifts from the declared domain, the domain gate turns red [2].
  • Typed wire contracts & output provenance. Every payload crossing a boundary — an extracted invoice, a structured assessment, a tool call, an agent verdict — decodes once into a strict schema (frozen Pydantic models and closed enums) that makes illegal states unconstructible, with every wire field self-described (the schema is the prompt) [2]. In high-trust workflows, every generated claim or rolled-up score carries a structured citation pointing back to its raw source span, turning disputes from arguments into evidence lookups.

Stage 04Evaluate without clean ground truth

Real business workflows rarely come with a clean labelled test set. Waiting for perfect labels stalls delivery; shipping without measurement invites silent failure. In my own pre-registered out-of-fold agent benchmark (MBPP+, n = 120), agents passing 98–100% of visible checks still failed full hidden test suites on roughly one task in six (~83% hidden pass), while an LLM judge systematically overestimated reliability (0.913 mean predicted pass vs 0.837 observed) FACT [3]. At the frontier, Scale Labs reported a similar 17.8-point gap between public (99.4%) and private (81.6%) sets on SWE-Bench Pro V2 FACT [4].

Three practical patterns hold when labels are scarce or expensive:

  1. Domain-expert golden sets & reconciliation lanes. Build a small, versioned set of real messy cases early — presswire duplicates, contested invoices, or expert-scored evaluation sheets — and build deterministic code that reconciles human scores against model outputs on the exact same hierarchy.
  2. Calibration and hidden folds. Always hold out cases the prompt-tuner or agent never sees. Score confidence calibration alongside ranking or precision so abstention thresholds reflect real risk rather than raw model logits.
  3. User corrections as a flywheel. Treat every human override in production as labelled training and error-analysis data — tracking correction rate by segment, supplier, or document class, while guarding against selection bias and delayed feedback.

Stage 05Prove every gate red and lock train/serve parity

Trust in production AI remains fragile: in Stack Overflow's 2026 developer survey, only 6.6% of developers reported trusting AI output for important decisions FACT [5]. Prose guidelines do not close that gap; mechanical verification does.

  • A gate is only a gate once seen red. An inert check looks identical to a clean codebase. In ini v0.3.0, all 13 deterministic gates (types, banned surfaces, AST module shape, complexity, ontology parity, public-surface behaviour tests, CRAP) must fail on a planted defect inside a scratch replica (--prove) before they count FACT [2].
  • Train/serve parity as an automated workflow. Whenever offline evaluation disagrees with live behaviour, trace the discrepancy to the exact feature, tokenization, or prompt transformation that drifted, fix the root cause, and freeze it with an automated parity test so that failure class cannot return quietly.
  • Cross-family review for non-mechanical judgement. Where no deterministic check can rule — requirements fidelity, subtle domain drift, architectural trade-offs — have a reviewer from a different model family inspect the contract and the artifact, returning concrete failing cases rather than adjectives [2].

Stage 06Handover, observability, and kill criteria

A system only counts as shipped when the team owning the product can monitor, debug, and change it without the original builder in the room.

  • Live failure dashboards tied to user trust. Monitor schema-parse failures, abstention/escalation rates, human correction rate, latency, token/compute cost per decision, and input distribution shift — not just HTTP 200s.
  • Progressive promotion. Shadow deployment first, then staged challenger-to-champion rollout gated by pre-set risk milestones, with one-step rollback to the deterministic or prior baseline.
  • Pre-registered kill criteria. Before scaling investment, write down what observed outcome — by what date — stops or reframes the system. Green gates prove internal correctness; they never prove product value or user adoption.

Where this discipline comes from

This playbook compresses patterns that held across domains — programmatic bidding, telecom risk, financial transaction categorization, news document similarity, mobile install prediction, and enterprise LLM assessment — into one transferable engineering loop. The concrete Python harness implementing Stages 02, 03, and 05 is open in github.com/adrianmatias/ini and mapped in ini: Constraining the Generative.
